# 評価ケース

`$test-extended-pencil` でケースの実行と採点を依頼できる。Taskで文書生成・採点のできるエージェントをケースごとに新規起動し、ケース間でセッションを共有しない。実行可能なTaskがなければ未実施と報告する。

`prompts/` の指示文と `expectations/` の期待結果は同じ番号・名前で対応する。`.opencode/skills/test-extended-pencil/.work/<実行ID>/<ケースID>/` にケースごとの作業ディレクトリを作り、引用された初回の依頼文だけを新しいTaskへ渡す。複数ターンのケースは最初の成果物と質問を保存してから、同じ `task_id` で追加回答を順に渡す。最後の成果物ができてから当該ケースの期待結果を渡して採点し、成果物・対話・行ごとの採点結果を保存する。親はケース別の報告を集約する。

各期待結果の表は、指示文にある事実・未決事項ごとに「確認先」と「期待する内容」を示す。表の1行を1項目として、満たせば1点、満たさなければ0点で採点する。期待結果で記載を求めていない節は省略してもよい。意味と確定・推測・未決の区別を採点し、指示文で指定された文字列以外は文面の一致を求めない。全項目を満たした場合に合格とし、未確認情報の確定事項への混入、または人間の回答で確定した内容の未反映は得点に関係なく不合格とする。各行の根拠、失敗理由、自己評価であることを報告し、修正前後で同じケースを比べる。

| ケース | 主な確認点 |
| --- | --- |
| 01 | 要件定義の初回作成と未決事項の質問 |
| 02 | 既存SQLから読み取った情報の扱い |
| 03 | 画面設計の状態と未決事項 |
| 04 | API契約にない情報を補わないこと |
| 05 | 回答後の確定・却下・新要件の反映 |
| 06 | 汎用文書と、未決事項がない場合の終了 |
| 07 | 確定したテーブル・参照をDBMLで表現すること |
| 08 | 汎用文書で旧資料からの推測を確定事項と分けること |
| 09 | 将来対応を現行機能や実施確約と混同しないこと |
| 10 | 確定DB構造と旧SQL由来の未確認構造の混在 |
| 11 | 画面のURL有無・クエリ・初期表示・外部デザインリンク |
| 12 | 画面のテキスト図、複数操作IDとエラー表示ID |
| 13 | 複数APIで認証不要と認証未確認を区別すること |
| 14 | 一部だけ確定したAPIエラーと未決の互換性 |
| 15 | 複数ターンでの推測の却下、確定、新しい未決事項 |
| 16 | 要件定義で細かな検討事項を基本設計へ申し送り、完了すること |

評価ケースは正解の文面を固定するためのものではない。期待結果は、文書に含めるべき事実、混入してはいけない推測、対話上の振る舞いを示す。実際の利用で新しい失敗が出たら、その状況を再現する指示文を追加する。
